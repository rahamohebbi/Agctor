# Product Requirements Document: Agctor System

## 1. Introduction

**Product Name:** Agctor System  
**Description:** A .NET-based actor model framework for building agentic systems with pluggable backends and extensible agent capabilities.

The Agctor System is designed to provide a robust foundation for developing agentic applications using the actor model pattern. It features a core SDK with swappable runtime backends, a standardized message protocol, and a CLI interface for interacting with agents.

## 2. Current System Capabilities

### 2.1 Core Architecture

#### 2.1.1 Actor Model Implementation
- ✅ **IActor Interface**: Fundamental contract for all actors with lifecycle management, message processing, and state tracking
- ✅ **Message Envelope**: Standardized message wrapper (IMessageEnvelope) with metadata, headers, and routing information
- ✅ **Pluggable Runtime Architecture**: Hot-swappable backend adapters using the IActorRuntimeAdapter interface
- ✅ **InMemory Runtime**: Fully functional in-memory actor runtime for development and testing

#### 2.1.2 Agent System
- ✅ **IAgent Interface**: Extension of IActor that provides agent-specific capabilities
- ✅ **Agent Factory**: Factory for creating and managing agents (IAgentFactory)
- ✅ **Agent Status Tracking**: States include Idle, Working, WaitingForSubtasks, WaitingForHumanInput, Completed, Failed
- ✅ **Agent Hierarchy**: Support for parent-child agent relationships with subtask delegation
- ✅ **Root Agent Architecture**: Primary coordinator agent that receives user requests and orchestrates task completion
- ✅ **Failure Handling**: Standardized approach for handling and reporting agent failures with appropriate error messages

#### 2.1.3 Message Communication Protocol (MCP)
- ✅ **Standardized Envelope**: All agents communicate using the standardized MCP envelope format
- ✅ **Metadata & Headers**: Support for rich metadata and headers for message routing and context
- ✅ **Serialization**: JSON serialization for message payloads (with planned support for other formats)
- ✅ **Hierarchical Communication**: Parent-child message passing with clear responsibility chains

#### 2.1.4 Error Handling and Logging
- ✅ **Centralized Error Handling**: Middleware-based approach for consistent error processing across the system
- ✅ **Error Context**: Standardized error context with source, exception details, and original message
- ✅ **Error Pipeline**: Support for pluggable error handlers in a processing pipeline
- ✅ **Standardized Logging**: Consistent logging interface (IAgctorLogger) with multiple severity levels
- ✅ **Console Logger**: Colorized console output with timestamps and categorization
- ✅ **Logger Factory**: Centralized logger creation and configuration
- ✅ **Dependency Injection**: Full integration with DI container for logging and error handling services

### 2.2 Implemented Features

#### 2.2.1 LLM Integration
- ✅ **LLMAgent**: Agent that communicates with local LLM (Ollama) to generate responses
- ✅ **HTTP Communication**: Support for making API calls to local LLM endpoints
- ✅ **Prompt Processing**: Ability to send prompts and receive responses from LLMs

#### 2.2.2 Tool Usage Framework
- ✅ **Tool Interface**: IToolActor interface for implementing tool functionality
- ✅ **Tool Request/Response**: Standardized ToolRequest and ToolResult structures
- ✅ **Tool Chaining**: Support for sequential execution of tools and forwarding data between steps

#### 2.2.3 Human Interaction
- ✅ **HumanAgentAdapter**: Special agent type that allows human input via CLI
- ✅ **Fallback Mechanism**: Ability for agents to delegate tasks to humans when they can't handle them
- ✅ **CLI Interaction**: Support for receiving multiline input from users via terminal

#### 2.2.4 CLI Interface
- ✅ **Command-line Utility**: Simple CLI for submitting prompts to the Agctor system
- ✅ **Runtime Selection**: Ability to specify which actor runtime to use
- ✅ **Status Monitoring**: Display of processing status and results in the console
- ✅ **Timeout Handling**: Support for maximum wait times on agent processing (5 minutes default)
  - Implements polling mechanism that checks agent status every 500ms
  - Provides progress updates every 10 seconds during long-running operations
  - Returns specific timeout message with current agent status if time limit is reached
  - Prevents agents from running indefinitely while providing user feedback

### 2.3 Development Tools
- ✅ **Dependency Injection**: Integration with Microsoft.Extensions.DependencyInjection
- ✅ **Logging**: Comprehensive logging with support for multiple severity levels and structured output
- ✅ **Error Handling**: Robust error handling with context preservation and standardized responses
- ✅ **Unit Testing**: Extensive test coverage for interfaces and components

#### 2.3.1 Code Execution
- ✅ **Multi-language Support**: Extensible architecture for executing code in different programming languages
- ✅ **C# Execution**: Dynamic compilation and execution of C# code using Roslyn
- ✅ **Python Execution**: Dynamic execution of Python code using IronPython
- ✅ **Language Detection**: Automatic language detection from file extensions
- ✅ **Alias Support**: Recognition of language aliases (e.g., "c#", "py", "python3")
- ✅ **Extensibility**: Pluggable architecture for adding new language executors

## 4. Limitations and Constraints

### 4.1 Runtime Support
- ✅ **InMemory Runtime**: Fully functional
- ⚠️ **Orleans Adapter**: Placeholder only, not yet implemented
- ⚠️ **Proto.Actor Adapter**: Placeholder only, not yet implemented

### 4.2 Performance Considerations
- Current implementation focuses on correctness rather than optimization
- Message processing is single-threaded within an actor
- No persistent state management implemented yet

### 4.3 Tool Ecosystem
- Limited number of tool implementations currently available
- Tool chaining mechanism is new and requires further testing with complex scenarios
- No standardized method for tool discovery or capabilities declaration

### 4.4 Language Support in CodeExecutorTool
- Currently supports C# and Python execution
- C# execution relies on Roslyn for dynamic compilation
- Python execution requires IronPython package
- Additional languages can be added through the extensible executor architecture

### 4.5 Agent Tracking and Monitoring
- Limited chronological tracking of agent operations
- No visualization layer for agent interaction flows
- Basic monitoring through console logs only

## 11. Recent Development Updates

### 11.1 Enhanced Logging Infrastructure

The logging system has been significantly enhanced with the addition of a robust file logging capability. This enhancement provides persistent storage of log data with sophisticated management features:

#### 11.1.1 Architectural Improvements
- **Provider Pattern**: The logging system now uses a provider-based architecture allowing multiple logging destinations simultaneously
- **Aggregate Logging**: Support for sending log entries to multiple targets (console, file, etc.) with a single API call
- **Factory Extensions**: Enhanced LoggerFactory with provider registration and management capabilities

#### 11.1.2 File Logger Features
- **Flexible Configuration**: Comprehensive options for controlling log file behavior:
  ```csharp
  var options = new FileLoggerOptions {
      LogDirectory = "logs/system",
      FileName = "{category}-{date}.log",
      RotationStrategy = RotationStrategy.Daily,
      MaxDaysToKeep = 30,
      MaxLogFiles = 50,
      CompressionStrategy = CompressionStrategy.OnRotation,
      ArchiveDirectoryStructure = ArchiveDirectoryStructure.ByYearMonth,
      MaxTotalSizeBytes = 1024 * 1024 * 1024 // 1GB total storage
  };
  ```
  
- **Rotation Strategies**:
  - Size-based: Create new log files when they reach a configurable size
  - Time-based: Daily, hourly, weekly, or monthly rotation with automatic date-based file naming
  - No rotation: Simple single-file logging for basic scenarios
  
- **Retention Management**:
  - Time-based cleanup: Automatically remove logs older than a specified number of days
  - Count-based limits: Maintain a maximum number of log files
  - Size-based limits: Keep total log storage under a specified size limit
  - Combined policies: Apply multiple constraints simultaneously
  
- **Compression and Archiving**:
  - Configurable compression on rotation or during cleanup
  - Hierarchical archive organization (flat, by year, by year/month)
  - Automatic archive directory creation and management
  - Custom file extension support for compressed files

- **Advanced Features**:
  - Background processing: Non-blocking logging for high-volume scenarios
  - Log statistics: Optional tracking and reporting of message counts by log level
  - Scheduled cleanup: Configurable times for performing maintenance operations
  - High performance: Optimized for minimal impact on application responsiveness

- **Performance Optimizations**:
  - Asynchronous I/O: Non-blocking write operations
  - Thread safety: Proper synchronization for multi-threaded environments
  - Minimal overhead: Efficient implementation with low impact on application performance

#### 11.1.3 Integration Improvements
- **DI Support**: Seamless integration with dependency injection frameworks:
  ```csharp
  services.AddSingleton<ILoggerProvider>(new FileLoggerProvider(options));
  ```
  
- **Multiple Logger Support**: Register and use different loggers for different purposes:
  ```csharp
  // All logs go to general file
  LoggerFactory.AddFileLogger(generalOptions);
  
  // Only errors go to dedicated error log
  LoggerFactory.AddFileLogger(errorOptions, LogLevel.Error);
  ```

#### 11.1.4 Future Expansion Path
The new provider architecture establishes a clear path for future logger implementations:
- Database loggers will follow the same provider pattern
- Cloud service integration (Azure Monitor, AWS CloudWatch, etc.)
- Third-party logging framework adapters (Serilog, NLog, etc.)

This enhanced logging infrastructure improves system observability and provides the foundation for more advanced monitoring and diagnostics capabilities in future releases.

### 11.2 Activity Tracking System Implementation

The Agctor activity tracking system has been fully implemented with the following key components:

#### 11.2.1 Core Abstractions
- **IActivityTracker**: Main interface for tracking activities across the actor system
  - Creates activity scopes with proper parent context propagation
  - Extracts and propagates context between components
  - Supports multiple backend implementations

- **IActivityScope**: Interface for a single traceable activity/span
  - Supports setting attributes for contextual information
  - Records events during the activity lifecycle
  - Captures exceptions with appropriate context
  - Sets activity status (Ok/Error) with optional descriptions
  - Implements IDisposable for automatic completion via using blocks

- **ActivityStatus**: Enum representing the status of an activity (Ok/Error)

#### 11.2.2 Multiple Implementations
- **Logger-Based Tracking**: Lightweight implementation using the Agctor logging system
  - Records activity start/end with timing information
  - Logs attributes, events, and exceptions
  - Minimal overhead for development scenarios
  - No external dependencies

- **OpenTelemetry-Based Tracking**: Full distributed tracing implementation
  - Integration with industry-standard observability protocol
  - Compatible with visualization tools like Jaeger and Zipkin
  - Support for distributed context propagation
  - Rich event and attribute recording

#### 11.2.3 Message Envelope Integration
- **Context Propagation**: Extension methods for propagating trace context via message headers
  - PropagateActivityContext: Adds current context to outgoing messages
  - ExtractActivityContext: Retrieves context from incoming messages
  - PayloadType: Utility for retrieving message type information

#### 11.2.4 Agent and Tool Integration
- **Transparent Instrumentation**: Decorator pattern for adding activity tracking without modifying core components
  - TracedAgent: Decorated IAgent implementation that creates activity spans for all operations
  - TracedToolActor: Decorated IToolActor implementation for tool usage tracking
  - TracingAgentFactory: Extended agent factory that wraps created agents with tracing

#### 11.2.5 Dependency Injection Support
- **Service Extensions**: Comprehensive registration methods for activity tracking services
  - AddAgctorActivityTracking: Registers the logger-based implementation
  - AddAgctorOpenTelemetryTracking: Configures and registers the OpenTelemetry implementation
  - Configuration options for customizing tracking behavior

#### 11.2.6 Usage Examples
```csharp
// Using the activity tracker directly
using (var activity = activityTracker.StartActivity("Process Data"))
{
    activity.SetAttribute("data_size", dataSize.ToString());
    
    try
    {
        // Do work
        activity.RecordEvent("Processing started");
        var result = ProcessData();
        activity.RecordEvent("Processing completed", new Dictionary<string, object>
        {
            { "records_processed", result.Count }
        });
        
        activity.SetStatus(ActivityStatus.Ok);
    }
    catch (Exception ex)
    {
        activity.RecordException(ex);
        activity.SetStatus(ActivityStatus.Error, ex.Message);
        throw;
    }
}
```

This implementation provides a robust foundation for tracking agent activities across the system, with flexibility to choose between lightweight logging-based tracking and full distributed tracing with OpenTelemetry. 

### 11.3 Metrics Collection System

The Agctor metrics collection system has been fully implemented with comprehensive support for monitoring actor and system performance:

#### 11.3.1 Core Abstractions
- **IMetricsCollector**: Primary interface for collecting various types of metrics
  - Counter metrics for tracking rates and counts
  - Gauge metrics for current values that can increase or decrease
  - Histogram metrics for distribution of values
  - Timer metrics for measuring operation durations
  - Configurable tags/dimensions for all metrics

- **OpenTelemetryMetricsCollector**: Implementation using OpenTelemetry metrics API
  - Standards-compliant integration with OpenTelemetry ecosystem
  - Support for multiple metric exporters (Prometheus, OTLP, etc.)
  - Efficient batching and aggregation of metrics

- **NoOpMetricsCollector**: Fallback implementation for when metrics are disabled
  - Zero-overhead placeholder when metrics aren't needed
  - Simplifies conditional logic by always providing a valid collector

- **MetricsConstants**: Centralized definitions of standard metric names
  - Actor-specific metrics (message counts, processing times)
  - Runtime-level metrics (actor counts, queue depths)
  - System health metrics (memory usage, thread counts)
  - Tool-specific metrics (invocations, execution time, success/failure counts)

#### 11.3.2 Actor Model Integration
- **MetricsEnabledActor**: Decorator pattern for transparent metrics collection
  - Wraps any IActor implementation to collect metrics without modifying core logic
  - Tracks message counts, processing times, and queue depths
  - Records actor lifecycle events (creation, activation, deactivation)
  - Captures errors and exception counts
  - Automatically detects tool actors and collects tool-specific metrics
  - Uses unified tagging system to provide actor category information

- **MetricsEnabledActorRuntimeAdapter**: Enhanced runtime with metrics capabilities
  - System-wide metrics for overall actor system health
  - Per-actor-type metrics for identifying patterns and bottlenecks
  - Runtime-specific metrics for adapter implementations

#### 11.3.3 Dependency Injection Support
- **MetricsServiceExtensions**: Simple registration of metrics services
  - AddMetricsCollection: Registers all required services
  - Configurable options for customizing metric collection behavior
  - Integration with other observability components

#### 11.3.4 Key Metrics Collected
- **Actor Performance**:
  - Message processing times (min/max/avg/percentiles)
  - Message throughput (messages per second)
  - Queue depth and waiting time
  - Actor count by type and status

- **System Health**:
  - Actor creation rate
  - Exception rate by actor type
  - Memory usage per actor type
  - Overall system throughput

- **Tool Metrics**:
  - Tool invocation counts by tool type and operation

#### 11.3.5 Recent Enhancements
The metrics system was recently enhanced to provide native support for tool metrics collection:

- **Unified Actor/Tool Approach**: Tools automatically benefit from the actor metrics system since they inherit from IActor
- **Tool-Specific Metrics**: Added dedicated metrics for tool operations (invocations, execution time, success/failure rates)
- **Smart Tool Detection**: The metrics decorator automatically detects if an actor is also a tool and adjusts its behavior
- **Rich Tagging**: All metrics include proper categorization (actor vs. tool) and operation-specific tags
- **Zero Configuration**: Tool authors don't need to add any metrics-specific code to their implementations

This approach ensures consistent metrics collection across both regular actors and tools while still providing tool-specific insights, maintaining the principle of "keep it simple and clean" by avoiding unnecessary code duplication.
