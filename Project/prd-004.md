# Product Requirements Document: Agctor System

## 1. Introduction

**Product Name:** Agctor System  
**Description:** A .NET-based actor model framework for building agentic systems with pluggable backends and extensible agent capabilities.

The Agctor System is designed to provide a robust foundation for developing agentic applications using the actor model pattern. It features a core SDK with swappable runtime backends, a standardized message protocol, and a CLI interface for interacting with agents.

## 2. Current System Capabilities

### 2.1 Core Architecture

#### 2.1.1 Actor Model Implementation
- ✅ **IActor Interface**: Fundamental contract for all actors with lifecycle management, message processing, and state tracking
- ✅ **Message Envelope**: Standardized message wrapper (IMessageEnvelope) with metadata, headers, and routing information
- ✅ **Pluggable Runtime Architecture**: Hot-swappable backend adapters using the IActorRuntimeAdapter interface
- ✅ **InMemory Runtime**: Fully functional in-memory actor runtime for development and testing with proper initialization
- 🔄 **Proto.Actor Runtime**: Phase 1 implementation complete with core actor operations, messaging, and statistics
- ✅ **Runtime Initialization**: Automatic runtime initialization during application startup with configuration support

#### 2.1.2 Agent System
- ✅ **IAgent Interface**: Extension of IActor that provides agent-specific capabilities
- ✅ **Agent Factory**: Factory for creating and managing agents (IAgentFactory) with multi-type support
- ✅ **Agent Type Registration**: Support for registering multiple agent types (Agent, LLMAgent, CodeExecutorTool) with the factory
- ✅ **Agent Status Tracking**: States include Idle, Working, WaitingForSubtasks, WaitingForHumanInput, Completed, Failed
- ✅ **Agent Hierarchy**: Support for parent-child agent relationships with subtask delegation
- ✅ **Agent Creation API**: RESTful endpoints for creating individual agents with type-specific configuration
- ✅ **Failure Handling**: Standardized approach for handling and reporting agent failures with appropriate error messages

#### 2.1.3 Message Communication Protocol (MCP)
- ✅ **Standardized Envelope**: All agents communicate using the standardized MCP envelope format
- ✅ **Metadata & Headers**: Support for rich metadata and headers for message routing and context
- ✅ **Serialization**: JSON serialization for message payloads (with planned support for other formats)
- ✅ **Hierarchical Communication**: Parent-child message passing with clear responsibility chains
- ✅ **HTTP to MCP Translation**: Seamless translation between HTTP requests and MCP message envelopes

#### 2.1.4 Error Handling and Logging
- ✅ **Centralized Error Handling**: Middleware-based approach for consistent error processing across the system
- ✅ **Error Context**: Standardized error context with source, exception details, and original message
- ✅ **Error Pipeline**: Support for pluggable error handlers in a processing pipeline
- ✅ **Standardized Logging**: Consistent logging interface (IAgctorLogger) with multiple severity levels
- ✅ **Console Logger**: Colorized console output with timestamps and categorization
- ✅ **Logger Factory**: Centralized logger creation and configuration
- ✅ **Dependency Injection**: Full integration with DI container for logging and error handling services

The modular scenario system enables quick setup of complex agent configurations:

- **Modular Architecture**: Easy to add new scenarios like "math-generation-chain" or custom workflows
- **Factory Pattern**: Centralized scenario creation with registration system
- **Configuration Support**: Scenario-specific parameters and customization options

**Core Components:**

- **ITimeoutPolicy Interface**: Defines timeout behavior with methods for GetTimeout(), ShouldReschedule(), and ShouldAbort()
- **ITimeoutSupervisor Interface**: Actor-based timeout monitoring with registration, cancellation, and progress tracking
- **TimeoutSupervisorActor**: Central supervisor that manages timeouts using message-passing without polling
- **Comprehensive Message Protocol**: Complete message hierarchy for timeout operations:
  - `RegisterTimeoutMessage`: Register new timeout monitoring
  - `CancelTimeoutMessage`: Cancel existing timeout
  - `UpdateProgressMessage`: Update timeout progress and reschedule if needed
  - `TimeoutTriggerMessage`: Internal timeout trigger mechanism
  - `TimeoutOccurredMessage`: Timeout notification with context
  - `CollectPartialResultsMessage/PartialResultsResponse`: Partial result collection

**Built-in Timeout Policies:**

- **FixedTimeoutPolicy**: Simple fixed-duration timeouts for consistent behavior
- **BudgetAwareTimeoutPolicy**: Respects parent agent timeout budgets with configurable buffer ratios
- **AdaptiveTimeoutPolicy**: Dynamically adjusts timeouts based on agent complexity and child count
- **AgentTypeTimeoutPolicy**: Agent-specific timeout configurations with type-based rules
- **CompositeTimeoutPolicy**: Combines multiple policies with strategies (minimum, maximum, or average)

**Extension Methods for Easy Integration:**

- `RegisterTimeoutAsync()`: Register timeout monitoring for agents
- `CancelTimeoutAsync()`: Cancel existing timeouts
- `UpdateProgressAsync()`: Update progress and trigger rescheduling
- `ExecuteWithTimeoutAsync()`: Automatic timeout management wrapper
- `CalculateChildTimeoutBudget()`: Hierarchical timeout budget calculation

**Key Features:**

- **Message-Passing Architecture**: No polling - uses Task.Delay with message-based cancellation
- **Hierarchical Coordination**: Parent agents can allocate timeout budgets to children
- **Progress Tracking**: Agents can report progress to extend timeouts dynamically
- **Fault Isolation**: Timeout failures are contained within actor boundaries
- **Scalability**: Message-based approach scales better than polling mechanisms
- **Partial Results**: Collect partial work when timeouts occur instead of losing everything
- **Runtime Agnostic**: Works with InMemory runtime and designed for Orleans/Proto.Actor compatibility

## 4. Limitations and Constraints

### 4.1 Runtime Support
- ✅ **InMemory Runtime**: Fully functional
- ⚠️ **Orleans Adapter**: Placeholder only, not yet implemented
- 🔄 **Proto.Actor Adapter**: Phase 1 implementation complete - core functionality working (spawning, messaging, statistics), Phase 2 planned for distributed deployment features

### 4.2 Performance Considerations
- Current implementation focuses on correctness rather than optimization
- Message processing is single-threaded within an actor
- No persistent state management implemented yet

### 4.3 Tool Ecosystem
- Limited number of tool implementations currently available
- Tool chaining mechanism is new and requires further testing with complex scenarios
- No standardized method for tool discovery or capabilities declaration

### 4.4 Language Support in CodeExecutorTool
- Currently supports C# and Python execution
- C# execution relies on Roslyn for dynamic compilation
- Python execution requires IronPython package
- Additional languages can be added through the extensible executor architecture

### 4.5 Agent Tracking and Monitoring
- Limited chronological tracking of agent operations
- No visualization layer for agent interaction flows
- Basic monitoring through console logs only

  ```csharp
  var options = new FileLoggerOptions {
  ```

  - Size-based limits: Keep total log storage under a specified size limit
  - Combined policies: Apply multiple constraints simultaneously
  
- **Compression and Archiving**:
  - Configurable compression on rotation or during cleanup
  - Hierarchical archive organization (flat, by year, by year/month)
  - Automatic archive directory creation and management
  - Custom file extension support for compressed files

- **Advanced Features**:
  - Background processing: Non-blocking logging for high-volume scenarios
  - Log statistics: Optional tracking and reporting of message counts by log level
  - Scheduled cleanup: Configurable times for performing maintenance operations
  - High performance: Optimized for minimal impact on application responsiveness

- **Performance Optimizations**:
  - Asynchronous I/O: Non-blocking write operations
  - Thread safety: Proper synchronization for multi-threaded environments
  - Minimal overhead: Efficient implementation with low impact on application performance

#### 15.1.3 Integration Improvements

### 25.4 Timeout Management System Implementation

The Agctor Timeout Management System has been fully implemented to provide comprehensive timeout handling for agent operations using the actor model:

#### 25.4.1 Core Architecture

The timeout management system is built on a message-passing architecture that leverages the actor model's strengths:

- **Message-Based Design**: No polling mechanisms - all timeout detection uses message passing for efficiency and scalability
- **Actor Supervision**: Integrates with actor supervision patterns for fault tolerance and isolation
- **Hierarchical Coordination**: Parent agents can allocate timeout budgets to child agents
- **Progress Tracking**: Agents can report progress to dynamically adjust timeouts

#### 25.4.2 Core Interfaces

- **ITimeoutPolicy**: Defines timeout behavior with three key methods:
  - `GetTimeout()`: Calculate timeout duration based on context
  - `ShouldReschedule()`: Determine if timeout should be extended based on progress
  - `ShouldAbort()`: Decide whether to abort operation on timeout

- **ITimeoutSupervisor**: Actor-based interface for timeout management:
  - `RegisterTimeoutAsync()`: Register timeout monitoring for agents
  - `CancelTimeoutAsync()`: Cancel existing timeouts
  - `UpdateProgressAsync()`: Update progress and potentially reschedule
  - `HandleTimeoutOccurredAsync()`: Process timeout events
  - `CollectPartialResultsAsync()`: Gather partial results on timeout

#### 25.4.3 Message Protocol

Complete message hierarchy extends `AgentMessage` base class:

- **RegisterTimeoutMessage**: Initiates timeout monitoring for an agent
- **CancelTimeoutMessage**: Cancels existing timeout monitoring
- **UpdateProgressMessage**: Reports progress and triggers rescheduling evaluation
- **TimeoutTriggerMessage**: Internal message for timeout scheduling
- **TimeoutOccurredMessage**: Notifies when timeout occurs with full context
- **CollectPartialResultsMessage/PartialResultsResponse**: Handles partial result collection

#### 25.4.4 Built-in Timeout Policies

- **FixedTimeoutPolicy**: Simple fixed-duration timeouts
  ```csharp
  var policy = new FixedTimeoutPolicy(TimeSpan.FromMinutes(5));
  ```

- **BudgetAwareTimeoutPolicy**: Respects parent timeout budgets
  ```csharp

  ```

- **AdaptiveTimeoutPolicy**: Adjusts based on agent complexity
  ```csharp

      baseTimeout: TimeSpan.FromMinutes(2),
      perChildTimeout: TimeSpan.FromSeconds(30),
      maxTimeout: TimeSpan.FromMinutes(30)
  );
  ```

- **AgentTypeTimeoutPolicy**: Type-specific timeout configurations
  ```csharp
  var policy = new AgentTypeTimeoutPolicy(defaultTimeout: TimeSpan.FromMinutes(5))
      .WithTypeTimeout<LLMAgent>(TimeSpan.FromMinutes(10))
      .WithTypeTimeout<CodeExecutorTool>(TimeSpan.FromMinutes(15));
  ```

- **CompositeTimeoutPolicy**: Combines multiple policies
  ```csharp
  var policy = new CompositeTimeoutPolicy(CompositeStrategy.Minimum)
      .AddPolicy(new FixedTimeoutPolicy(TimeSpan.FromMinutes(10)))
      .AddPolicy(new BudgetAwareTimeoutPolicy(TimeSpan.FromMinutes(5)));
  ```

#### 25.4.5 TimeoutSupervisorActor Implementation

The `TimeoutSupervisorActor` provides centralized timeout management:

- **Non-Polling Architecture**: Uses `Task.Delay` with `CancellationToken` for efficient timeout scheduling
- **Concurrent Timeout Management**: Tracks multiple timeouts simultaneously using `ConcurrentDictionary`
- **Message-Based Cancellation**: Cancels timeout tasks via message passing rather than polling
- **Progress Integration**: Evaluates progress updates and reschedules timeouts when appropriate
- **Partial Result Collection**: Coordinates partial result gathering when timeouts occur
- **Fault Tolerance**: Handles exceptions gracefully and maintains timeout state consistency

#### 25.4.6 Extension Methods

Convenient helper methods for easy integration:

```csharp
// Register timeout monitoring
await agent.RegisterTimeoutAsync(timeoutSupervisor, policy, parentBudget);
```

## 27. Intent Resolution & Natural-Language Search Enhancements (July 2025)

### 27.1 Feature Overview
The Code Understanding subsystem now includes a fully-fledged **intent-resolution pipeline** that lets agents understand *what* the user wants before deciding *how* to answer.  The pipeline follows a **chain-of-responsibility** pattern so that additional resolvers can be plugged in at runtime.

| Component | Purpose |
|-----------|---------|
| `IntentKind` | Canonical list of intents (ListClasses, ShowMethodBody, SemanticSearch …) |
| `IntentResolution` | Result object exposing `Kind`, `Confidence`, and optional `Arguments` |
| `IIntentResolver` | Contract for pluggable resolvers – returns `IntentResolution?` |
| `HeuristicIntentResolver` | Fast keyword/regex matcher for common structural queries |
| `RegexIntentResolver` | Power-user regex patterns for fine-grained matching |
| `LlmIntentResolver` | Falls back to LLM when heuristics fail; uses `ILlmClient` |
| `ProxyIntentResolver` | Delegates to a remote agent/network for cross-process intent detection |
| `IntentDetectionAgent` | Actor wrapper around `LlmIntentResolver` so LLM calls run off the hot-path |

### 27.2 SearchAgent Refactor
* `SearchAgent` now accepts an **ordered list of `IIntentResolver`s** via DI.
* If no resolver yields a confident match, **vector search** is used as a final fallback.
* Structural queries (e.g., "list classes") bypass the LLM entirely, reducing latency and token spend.
* Removed brittle hard-coded helper methods (`IsListClasses`, etc.) in favour of resolver composition.

### 27.3 QueryAgent Improvements
* Detects when the returned STRUCTURAL CONTEXT is already the answer and instructs the LLM to *re-format only*, preventing hallucinations.
* Lazy loading of code snippets – snippets are fetched only when the LLM actually needs them.

### 27.4 Demo Scenario Updates
* `CodeGraphDemoScenario` now wires: `HeuristicIntentResolver` → `RegexIntentResolver` → `ProxyIntentResolver` → **LLM-powered** `IntentDetectionAgent`.
* Sample workspace upgraded to a **multi-file calculator library** demonstrating class hierarchy and utilities.

  * `RegexIntentResolverTests`
