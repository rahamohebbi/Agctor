# Agctor harness assessment and development priorities

Assessment date: October 8, 2026. Repository reviewed: `5ef73c2`.

This assessment uses “harness” to mean the software around the model: context selection, tools, execution state, orchestration, permissions, recovery, verification, and evaluation. Findings come from source inspection and current primary documentation. No runtime benchmarks or test suites were run for this assessment. Proposed capabilities and acceptance criteria below are not claims about current behavior.

Agctor's most promising direction is a runtime for long-lived agents that maintain reviewable knowledge about a project and its entities. The actor architecture, entity-resolution evidence, canonical project files, scenario flows, and CodeGraph provide useful foundations for that direction. The next investment should make those capabilities reliable and measurable.

There is no evidence here that competitors cannot implement any of these ideas. Persistent memory, graph workflows, multi-agent delegation, local models, and file-backed knowledge already exist elsewhere. Agctor's differentiation must come from the integrated behavior and demonstrated results.

## What to learn from other projects

| Reference | Verified pattern | Application to Agctor |
| --- | --- | --- |
| [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence) | Distinguishes thread checkpoints from cross-thread memory stores; supports persistence for continuation and recovery. | Separate run state from canonical project knowledge. Version both and record the knowledge versions used by a run. |
| [Microsoft Agent Framework checkpoints](https://learn.microsoft.com/en-us/agent-framework/workflows/checkpoints) | Saves executor states, pending messages, pending requests/responses, and shared state at superstep boundaries. | A checkpoint must capture enough execution state to continue, not just the current node's name and final output. This is a relevant .NET reference. |
| [Deep Agents](https://docs.langchain.com/oss/python/deepagents/overview) | Summarizes history, offloads large results, loads knowledge when needed, and delegates into isolated contexts. | Build one context service that pins requirements, selects relevant evidence, and passes bounded context to delegated work. |
| [OpenHands SDK](https://docs.openhands.dev/sdk/arch/overview) and [design principles](https://docs.openhands.dev/sdk/arch/design) | Separates agent, tools, workspace, and server; provides typed events and configurable execution environments. Isolation is optional in its current design. | Keep one policy boundary for tool execution and offer explicit local and isolated workspace modes. Reuse the same run contract across CLI, API, and UI. |
| [Letta memory](https://docs.letta.com/agent-sdk/memory) | Maintains memory across conversations, separates always-in-context files from on-demand files, and supports background consolidation. Its current memory model also uses Git. | Add a small working-memory layer and controlled background reconciliation. File-backed or Git-backed memory alone is not a uniqueness claim for Agctor. |
| [Anthropic harness experiments](https://www.anthropic.com/engineering/harness-design-long-running-apps) | Uses explicit completion criteria and a separate evaluator; also shows that harness complexity and cost should be reconsidered as models improve. | Require verifiable completion evidence, and retain additional agents only when evaluations justify their cost. |
| [MCP transport specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) | Uses JSON-RPC and defines stdio and Streamable HTTP standard transports; permits custom transports. | Keep internal actor messaging independent of an external standards-compatible MCP server. Use the official C# SDK where it fits. |

These are patterns to adapt or integrate, not a recommendation to replace the actor runtime with another framework.

## Development backlog in dependency order

**1. Establish an outcome baseline.** Create a small versioned evaluation suite covering repository edits, long conversations, ambiguous entities, corrections, interrupted runs, and repeated events. Reuse existing unit/integration tests for correctness, and add live-model evaluations for task outcomes. Record model/version, prompts, tools, initial workspace, token use, elapsed time, verification results, and user interventions. Compare a simple single-agent baseline, baseline plus ordinary retrieval, and the full Agctor configuration using the same models and task budgets. Use repeated runs and held-out tasks. Exit criterion: every subsequent harness change produces a comparable report, with separate quality, cost, and recovery results.

**2. Define a shared run contract and durable execution journal.** Include run/task/step identifiers, parent-child relationships, plan version, inputs, recorded tool results, pending approvals/events, deadlines, and cumulative budgets. Persist the intent to execute a step and its result around side effects. Use SQLite transactions locally and a replaceable distributed store later. Add idempotency keys for cooperating tools, event deduplication, an outbox for event delivery, and reconciliation for actions whose external outcome is unknown. Do not promise universal exactly-once external execution. Exit criterion: failure injection before and after every boundary either resumes correctly or reports an explicit uncertain action without blindly repeating it.

**3. Replace character truncation with explicit context selection.** Preserve the task, current constraints, acceptance criteria, unresolved questions, and relevant evidence references. Budget using model-appropriate token accounting. Store large tool outputs as artifacts and retrieve relevant slices. Version summaries; preserve source links and unresolved conflicts. Separate instruction-bearing configuration from untrusted retrieved text. Exit criterion: long-session tasks retain their initial constraints after repeated compaction and a fresh-session handoff, with measured context cost and answer quality.

**4. Unify tools, permissions, and resource budgets.** Define structured tool arguments and results, workspace scope, side-effect classification, cancellation behavior, output caps, retry rules, and budget charging. Enforce policy before all tool entry points, including retries and resumed/delegated work. Execute generated code in an explicitly isolated workspace when required, with enforceable filesystem/network/process limits. Add bounded actor queues and per-model concurrency control. Existing step/loop limits are useful, but should share a run-wide budget across descendants. Exit criterion: runaway code can be terminated; a child cannot bypass its parent's restrictions; queue overload has a predictable response; replay does not reset the budget.

**5. Make completion depend on evidence.** Generalize CoderAgent's existing gates into task-specific verifiers: project builds, relevant tests, structured output checks, memory invariants, and application behavior. Return structured edit paths instead of parsing human-readable output. Permit bounded repair after validation failure and persist each attempt. Separate worker output from verifier results. Exit criterion: a task cannot be marked successful when its declared acceptance checks fail, and repair effort remains within the run budget.

**6. Establish real external interoperability.** Add a standards-compatible MCP boundary using JSON-RPC, initialization/capabilities, tool schemas, cancellation, and a supported standard transport. Exercise it with an independent standard client. Distinguish this public interface from the internal actor envelope in documentation. A provider-neutral model interface should likewise expose streaming, structured output, tool use, usage accounting, and capability differences without forcing everything into plain prompt strings. Exit criterion: a standard client discovers and calls tools without an Agctor-specific transport shim; changing a model backend preserves typed run results and budget accounting.

**7. Strengthen Agctor's distinctive memory behavior.** Extend identity-link evidence into a fact lifecycle: origin, valid time, observation time, evidence, approval, correction/supersession, and deletion. Distinguish a claim changing over time from contradictory claims about the same time. Calibrate entity-link thresholds on labeled examples; do not display weighted scores as proven probabilities. Version learned routing rules, record the approval that introduced each rule, test its scope, and support rollback. Exit criterion: ambiguous names do not silently merge, corrections reach retrieval, and an approved routing rule improves future handling without misrouting unrelated facts.

**8. Develop active CodeGraph behavior, then prove runtime scale.** Start with incremental C# semantic dependencies, stable symbol identities, nested-file changes, renames/deletions, and affected-test discovery. Let actors represent inexpensive state and coordination; invoke a model only when needed. Attach project decisions and evidence to affected symbols so changes can be checked against prior constraints. After single-process guarantees are measured, implement actual Orleans grains and distributed state for a selected actor type and run a shared runtime conformance suite. Exit criterion: graph-informed changes reduce missed dependencies or verification cost at equal task success, and remote actor execution survives node loss without corrupting state.

## The advantages worth proving

**Reviewable entity memory.** Demonstrate several sessions mentioning two entities with similar names, followed by a user correction. Show the evidence behind each link, reverse an incorrect decision, and update downstream retrieval. Existing resolution actors and transition records make this a credible near-term focus. Full fact reconciliation remains proposed work.

**Learning from an approved correction.** Demonstrate a previously unknown fact type entering the review inbox, approval creating a routing rule, a subsequent valid fact using that rule, and an unrelated fact remaining outside it. Measure repeat-approval burden and misrouting, not just whether a rule file was written.

**An executable model of a project.** Demonstrate a contract change reaching affected files, tests, and relevant project decisions, followed by a verified patch. This combines CodeGraph with memory and actor coordination. It is an intended capability that needs substantial work beyond the existing structural hierarchy.

**Portable knowledge with replaceable infrastructure.** Demonstrate rebuilding derived indexes from canonical project data and changing a retrieval provider while preserving entity identities, evidence, and answers. Extend this to distributed execution only after the Orleans implementation actually runs agents remotely. Portability is an engineering value proposition; it is not unique in isolation.

The first release milestone should combine evaluation, durable runs, context preservation, and tool boundaries with one polished entity-memory demonstration. Follow it with verified CodeGraph changes. Prioritize additional runtimes, providers, and agent roles when these measured workloads show a need.
